# Constitucion del Backend

## 1. Proposito

Este documento define la base tecnica y las fases de construccion del backend
para el sistema de reservas de mesas del restaurante.

El backend expondra una API REST para administrar la autenticacion del
administrador y las reservas almacenadas en la base de datos `reservadb`.

## 2. Alcance funcional

El backend debe implementar las siguientes funcionalidades:

1. Inicio de sesion del administrador.
2. Cierre de sesion del administrador.
3. Registro de una reserva.
4. Actualizacion de una reserva.
5. Listado de reservas.
6. Listado filtrado de reservas.

Todas las operaciones de reservas requieren un administrador autenticado.

## 3. Tecnologias

| Area | Tecnologia | Decision |
| --- | --- | --- |
| Lenguaje | TypeScript | Tipado estatico y configuracion estricta. |
| HTTP | Hono.js | Framework ligero para la API REST. |
| Runtime | Node.js | Runtime de Vercel para soportar Hono, MySQL y bcrypt. |
| Despliegue | Vercel | Cada ruta se ejecutara como una Vercel Function. |
| Autenticacion | JWT | Tokens firmados para proteger los endpoints. |
| Hash de contrasenas | bcrypt | Factor de costo `8`; nunca se almacenan contrasenas en texto plano. |
| Validacion | Zod | Validacion de cuerpos, parametros y filtros. |
| Base de datos | PostgreSQL 15+ | Base relacional principal del sistema. |
| Driver de base de datos | pg | Pool de conexiones y API basada en promesas. |
| Pruebas | Vitest | Pruebas unitarias e integracion. |

## 5. Arquitectura

Se utilizara una arquitectura de tres capas. Es preferible a un MVC puro para
este proyecto porque separa las reglas de negocio de Hono y de las consultas
SQL, facilitando las pruebas y el mantenimiento.

```text
backend/
├── src/
│   ├── index.ts
│   ├── routes/
│   ├── controllers/
│   ├── services/
│   ├── repositories/
│   ├── schemas/
│   ├── middleware/
│   ├── lib/
│   ├── db/
│   └── types/
├── tests/
├── package.json
├── tsconfig.json
└── .env.example
```

### 5.1 Capa de presentacion

Responsabilidades:

- Definir las rutas HTTP de Hono.
- Leer parametros, query strings y cuerpos JSON.
- Ejecutar validaciones Zod.
- Aplicar middleware de autenticacion.
- Convertir los resultados a respuestas HTTP.
- No contener consultas SQL ni reglas de negocio complejas.

Componentes principales:

- `routes/`
- `controllers/`
- `schemas/`
- `middleware/`

### 5.2 Capa de aplicacion

Responsabilidades:

- Implementar los casos de uso.
- Comparar credenciales con bcrypt.
- Crear y validar la informacion del token JWT.
- Aplicar reglas de reservas.
- Traducir errores de negocio a errores controlados.

Componentes principales:

- `services/auth.service.ts`
- `services/reserva.service.ts`

Los servicios dependeran de interfaces de repositorio y no de una
implementacion concreta de MySQL.

### 5.3 Capa de infraestructura

Responsabilidades:

- Crear y administrar el pool de conexiones MySQL.
- Implementar los repositorios.
- Leer variables de entorno.
- Proveer bcrypt y la configuracion JWT.

Componentes principales:

- `db/pool.ts`
- `repositories/administrador.repository.ts`
- `repositories/reserva.repository.ts`
- `lib/config.ts`
- `lib/password.ts`
- `lib/jwt.ts`

## 6. Modelo de datos

La base de datos se llama `reservadb` y contiene las tablas:

### Administrador

- `Identificador`: identificador primario.
- `Usuario`: maximo 15 caracteres.
- `Contrasena`: hash bcrypt de 60 caracteres.

### tablaReserva

- `Identificador`: identificador primario.
- `NombreCliente`: nombre del cliente.
- `NumeroCliente`: numero telefonico almacenado como texto.
- `EstadoPedido`: solo `Disponible` o `Cancelado`.
- `NumeroMesa`: numero de mesa.
- `FechaReserva`: fecha y hora de la reserva.

El backend debe respetar las restricciones definidas en los scripts SQL de
`db/`. La contrasena inicial del administrador debe almacenarse como un hash
bcrypt, nunca como texto plano.

## 7. Autenticacion y seguridad

### Inicio de sesion

`POST /api/auth/login` recibira:

```json
{
  "usuario": "sabinofc",
  "contrasena": "..."
}
```

El servicio debe buscar el administrador por usuario y comparar la contrasena
recibida con `bcrypt.compare`. El hash se generara con:

```ts
await bcrypt.hash(contrasena, 8)
```

Una autenticacion exitosa devolvera un JWT sin incluir la contrasena ni su
hash en el payload.

### JWT

- Algoritmo inicial: `HS256`.
- Secreto: variable `JWT_SECRET`.
- Emisor: variable `JWT_ISSUER`.
- Audiencia: variable `JWT_AUDIENCE`.
- Expiracion: variable `JWT_EXPIRES_IN`.
- Identidad del administrador: claim `sub`.

Las rutas de reservas usaran el header:

```text
Authorization: Bearer <token>
```

El secreto nunca se debe incluir en el codigo, en el repositorio ni en los
logs.

### Cierre de sesion

El JWT es stateless. El endpoint `POST /api/auth/logout` confirmara el cierre
de sesion y el cliente debera eliminar el token almacenado.

Para invalidar tokens inmediatamente en el servidor se requerira una futura
tabla de sesiones o una lista de revocacion persistente. No se usara una lista
en memoria porque no es confiable entre instancias de Vercel.

## 8. API REST

### Autenticacion

| Metodo | Ruta | Auth | Descripcion |
| --- | --- | --- | --- |
| `POST` | `/api/auth/login` | No | Autentica al administrador y devuelve un JWT. |
| `POST` | `/api/auth/logout` | Si | Solicita el cierre de sesion del cliente. |

### Reservas

| Metodo | Ruta | Auth | Descripcion |
| --- | --- | --- | --- |
| `POST` | `/api/reservas` | Si | Registra una reserva. |
| `PATCH` | `/api/reservas/:id` | Si | Actualiza una reserva existente. |
| `GET` | `/api/reservas` | Si | Lista las reservas. |
| `GET` | `/api/reservas?estado=Disponible` | Si | Filtra por estado. |

Los filtros podran incluir, como minimo:

- `estado`.
- `fechaDesde`.
- `fechaHasta`.
- `numeroMesa`.
- `nombreCliente`.

Los nombres finales de los campos del JSON deben mantenerse consistentes y
documentarse antes de implementar el frontend.

## 9. Validacion y errores

Zod validara:

- Usuario y contrasena del login.
- Nombre, telefono, estado, mesa y fecha de una reserva.
- Identificadores de ruta.
- Parametros de filtrado.

Respuestas esperadas:

- `200`: operacion exitosa.
- `201`: recurso creado.
- `400`: datos invalidos.
- `401`: token ausente, invalido o credenciales incorrectas.
- `404`: administrador o reserva no encontrados.
- `409`: conflicto de datos.
- `500`: error interno no expuesto al cliente.

Los errores deben tener un formato uniforme:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Los datos enviados no son validos",
    "details": []
  }
}
```

No se deben devolver stack traces, secretos, hashes ni detalles internos de
la base de datos.

## 10. Compatibilidad con Hono y Vercel

La documentacion oficial de Hono indica que una aplicacion puede desplegarse
en Vercel con configuracion cero cuando exporta la instancia de Hono como
`default` desde una entrada reconocida.

El punto de entrada sera `src/index.ts`:

```ts
import { Hono } from 'hono'

const app = new Hono()

export default app
```

Vercel reconocera `src/index.ts` como la entrada de la aplicacion Hono sin un
`vercel.json` personalizado. Para desarrollo local se utilizara:

```bash
vc dev
```

La configuracion debe apuntar al runtime Node.js. Esto es necesario para
utilizar las APIs de Node requeridas por `bcrypt` y `pg`. No se debe
configurar el proyecto para Edge Runtime mientras se use el paquete nativo
`bcrypt`.

La documentacion oficial de Hono tambien permite crear el middleware JWT con
`hono/jwt`, usando el secreto desde `c.env` o desde la configuracion de la
aplicacion. En este proyecto se utilizara la configuracion validada de entorno.

Fuentes consultadas:

- [Hono en Vercel](https://hono.dev/docs/getting-started/vercel)
- [Hono en la documentacion de Vercel](https://vercel.com/docs/frameworks/backend/hono)
- [Middleware JWT de Hono](https://hono.dev/docs/middleware/builtin/jwt)
- [Runtime Node.js de Vercel](https://vercel.com/docs/functions/runtimes/node-js)
- [bcrypt para Node.js](https://github.com/kelektiv/node.bcrypt.js)

## 11. Variables de entorno

El archivo `.env.example` debe documentar:

```text
NODE_ENV=development
PORT=3000
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/reservadb
DATABASE_SSL=false
JWT_SECRET=
JWT_ISSUER=reservadb-api
JWT_AUDIENCE=reservadb-client
JWT_EXPIRES_IN=1h
CORS_ORIGIN=http://localhost:3000
```

Los valores reales se configuraran localmente o en Vercel Environment
Variables, nunca en archivos versionados.

## 12. Fases de construccion

### Fase 1: Constitucion del proyecto

- Crear el proyecto TypeScript.
- Crear `package.json` y fijar una version estable de Node.js.
- Instalar dependencias de produccion y desarrollo.
- Configurar `tsconfig.json` con modo estricto.
- Crear `.env.example`.
- Crear el punto de entrada `src/index.ts`.

### Fase 2: Infraestructura de datos

- Configurar el pool `pg` usando `DATABASE_URL`.
- Validar las variables de entorno con Zod al iniciar.
- Implementar repositorio de administradores.
- Implementar repositorio de reservas.
- Verificar conexion contra `reservadb`.
- Preparar la migracion de la contrasena inicial a bcrypt.

### Fase 3: Seguridad transversal

- Implementar hashing y comparacion asincrona con bcrypt.
- Implementar emision y verificacion JWT.
- Crear middleware de autenticacion.
- Configurar CORS.
- Crear middleware global de errores.
- Evitar filtracion de credenciales en logs y respuestas.

### Fase 4: Autenticacion

- Crear schema Zod para login.
- Implementar `POST /api/auth/login`.
- Implementar `POST /api/auth/logout`.
- Probar credenciales validas e invalidas.
- Probar tokens vencidos, alterados y ausentes.

### Fase 5: Gestion de reservas

- Crear schemas Zod de alta, actualizacion y filtros.
- Implementar `POST /api/reservas`.
- Implementar `PATCH /api/reservas/:id`.
- Implementar `GET /api/reservas`.
- Implementar filtros y paginacion basica.
- Verificar los estados `Disponible` y `Cancelado`.

### Fase 6: Pruebas y calidad

- Crear pruebas unitarias de servicios.
- Crear pruebas de repositorios contra una base de datos de prueba.
- Crear pruebas HTTP con el cliente de testing de Hono.
- Verificar codigos HTTP y formato de errores.
- Configurar lint y comprobacion de tipos.

### Fase 7: Despliegue

- Configurar el runtime Node.js en Vercel.
- Registrar las variables de entorno por ambiente.
- Ejecutar el build de produccion.
- Ejecutar `vc dev` para validar el comportamiento local de Vercel.
- Desplegar una preview.
- Ejecutar pruebas de humo sobre la preview.
- Promover a produccion despues de validar autenticacion y reservas.

## 13. Criterios de aceptacion

- El proyecto compila sin errores de TypeScript.
- La API inicia localmente y responde a un endpoint de salud.
- El administrador puede iniciar sesion con credenciales validas.
- Las credenciales invalidas producen `401` sin revelar informacion sensible.
- Las rutas de reservas rechazan peticiones sin JWT valido.
- Se pueden registrar y actualizar reservas validas.
- Se pueden listar reservas y aplicar filtros.
- Los valores de estado invalidos son rechazados por Zod y por la base de datos.
- Las contrasenas almacenadas tienen formato bcrypt y costo `8`.
- La aplicacion puede ejecutarse como Vercel Function usando Node.js.
